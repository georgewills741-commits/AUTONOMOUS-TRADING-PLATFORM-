## Writing a contract

A contract is a subclass of `atp.contracts.Contract`, a Pydantic v2 model (TEC-004). It declares its own identity and version:

```python
class Leg(Contract):
    contract_id = "atp.example.leg"
    contract_version = ContractVersion(1, 0)
    price: Amount
    venue: str
```

| Convention | How the code enforces it | Tests |
|---|---|---|
| **Identity and version on every contract.** Each subclass declares its own `contract_id` and `contract_version`; an inherited one does not count | Checked when the class is defined (`TypeError`). The identity is lowercase letters and digits in parts joined by dots or hyphens, starting with a letter, because it names the contract's directory of committed schemas. Two of the platform's contracts with one identity fail when the schemas are produced | `tests/contracts/test_model.py`, `tests/contracts/test_schemas.py` |
| **Strict.** No value is converted to another type: the text `"1"` is not an integer, a JSON `true` is not 1, and in Python input a list is not a tuple. JSON arrays are read as tuples, and a mapping is read as a nested contract. Pydantic's strict mode still converts in a few cases: from Python, an instance of a subclass of `str`, `int`, `tuple`, or `frozenset` (an enum member that is also text or an integer, a named tuple) is read as the plain value, while one of a subclass of a date, a time, a datetime, a duration, or a UUID is kept as given; and a `float` field also takes any other value Python turns into a float except a `bool` (an `int`, a `Decimal`, a `Fraction`, an object with `__float__`), as the nearest float, so an amount given to a float field loses its exactness without an error, which only review catches ([numerical policy](numerical-policy.md)). And dates, times, datetimes, durations, and UUIDs read text in Pydantic's formats, which are wider than the form they are written in: a date or a datetime also reads a Unix timestamp written as text (`"86400"` is 1970-01-02, and `"1"` is 1970-01-01T00:00:01Z, time-zone-aware), a time or a datetime holds naive and time-zone-aware values alike, a time and a duration also read `"01:02"`, and a UUID also reads its digits without hyphens, in braces, after `urn:uuid:`, or in capitals. Whether these read only their written form, and whether a time or a datetime must be time-zone-aware, are decided at checkpoint C, as is whether a float field refuses a `Decimal`. Pydantic matches literals and enums by equality, even in strict mode, and `True == 1 == 1.0`: so only the literals and enums it reads strictly are field types (next row) | Pydantic's strict mode, also inside an outcome's value and error; the field types of the next row | `tests/contracts/test_model.py`, `tests/contracts/test_outcome.py` |
| **Immutable, nested values included.** Assigning to a field or deleting one raises `AttributeError` with fixed text (Pydantic's own refusal would repeat the assigned value). A field holds only immutable types: `str`, `int`, `bool`, `float`, `None`, dates, times, datetimes, durations, UUIDs, enums whose members' values are strings (a member's value is reachable through every contract that holds it) or `IntEnum`s, which Pydantic reads as integers (another enum of integers would read JSON `true` and `1.0` as the member 1), and that read only their own members (no `_missing_` of their own or from a base enum, a fallback or case-insensitive lookup that would read other values as a member; so no flag, whose `_missing_` from `Flag` reads combinations of members, and from JSON `true` and `false`), literals whose values are strings or `None` (a literal of `1` would read JSON `true` and `1.0`, one of `True` would read `1`, and one of an enum member its bare value from Python), `Amount`, `IdempotencyKey`, other contracts, outcomes, and tuples, frozensets, and unions of these. A union holds at most one member of each kind of JSON value (text, number, boolean, object, array; null aside, which every member reads as `None`): its written form does not say which member a value came from, and reading it picks the first member that accepts the value, so a withdrawal written beside a deposit with the same fields would come back as a deposit, and a date beside text as text. So two contracts, two outcomes, or a contract and an outcome; text beside a date, a time, a datetime, a duration, a UUID, a key, an amount, or an enum of strings; an `int` beside a `float` or an `IntEnum`; and a tuple beside a frozenset are refused. A literal stands beside another member written as text only beside `str`, or beside an amount with text outside the amount's text form (`Amount \| Literal["market"]`, not `Literal["1"]`). An amount stands in a union only beside `None` or a literal of strings (row below), and an idempotency key only beside `None`: the writers of both write any value they are given as text, and a union can give them another member's value (`IdempotencyKey \| int` would write 7 as "7"). A union written inside metadata is part of the union around it: `Annotated[Amount \| None, Field(gt=0)] \| float` is an amount beside a float. Collections are tuples (`tuple[Leg, ...]`), never lists, sets, mappings, or `Any`. No `bytes`: JSON has none, so binary data gets an encoding by decision when a contract first needs it. A type alias made with a `type` statement is refused, `Amount` excepted, because it would hide its value from these checks; an alias made by assignment (`Legs = tuple[Leg, ...]`) is the type itself and is checked as such. A `NewType` (`OrderId = NewType("OrderId", str)`) and a generic contract whose fields use its type parameters are refused when the class is defined, like any type not listed; a later contract that needs one adds it to the kernel's lists, with its tests. A frozenset is written as an array in an order that can differ between processes (string hashing is randomized per process), so a contract whose written form must be stable (for a hash, a signature, or a byte comparison) holds a tuple | Pydantic's frozen models and an overridden `__setattr__`; every field's type is checked against that list when the class is defined, at any depth (`TypeError`), and a type that cannot be resolved then is refused too. A float is allowed only for values that are not amounts (TEC-003), which review checks | `tests/contracts/test_model.py` |
| **Unknown fields are refused** | `extra="forbid"` | `tests/contracts/test_model.py` |
| **One name per field.** A field with an alias is read and written under the alias, so a contract reads its own JSON and its written form matches its committed schema | `serialize_by_alias=True`; a second name for reading or writing is refused | `tests/contracts/test_model.py` |
| **What a contract may add is listed; everything else is refused.** Its settings are exactly the base's (strictness, immutability, unknown fields, hidden input, validated defaults, re-validation, finite floats, writing under the alias): changing one, or adding any other (`json_encoders`, `use_enum_values`, `coerce_numbers_to_str`, a title), in its own `model_config` or by inheriting from another model, is refused. A field's metadata is written only as `Field(...)`, holding the constraints it expresses (`gt`, `ge`, `lt`, `le`, `multiple_of`, `min_length`, `max_length`, `pattern`, `max_digits`, `decimal_places`, and `strict=True`), and as `AfterValidator(...)`: exactly those classes, never a subclass, which could read the input before the declared type does. A constraint object written directly (`annotated_types.Gt(1)`, `Strict()`), before, plain, and wrap validators, serializers, and any other metadata are refused, at any depth, and no field turns strictness off or allows infinities. A field's other settings are only its default (a value or a `default_factory`), alias, title, description, examples, `json_schema_extra` (a mapping whose keys are extensions starting with `x-`, so it cannot restate a JSON Schema keyword such as `type` or `minimum`, nor be a function that rewrites the schema), `deprecated`, and `repr`: a second name for reading or writing (`validation_alias`, `serialization_alias`, `AliasChoices`, `AliasPath`), a discriminator, a per-field `frozen`, `field_title_generator`, and the dataclass settings (`init`, `init_var`, `kw_only`) are refused, on a field and on a `Field(...)` written inside a type alike. An amount's bound is an amount or an integer, never a float, text, or a bool, also on an optional amount, and in a union written inside metadata; and an amount, with or without constraints or validators of its own, also in a union written inside metadata, is combined in a union only with `None` or a literal of strings (`Amount \| Literal["market"]`), since another branch would accept what the amount refuses, and the literal's text is outside the amount's text form (the union rule above). Python's `typing` caches `Annotated[...]` by equality, and a constraint object equals one holding an equal value of another type (`Gt(1.0) == Gt(1) == Gt(True)`), so a constraint written directly could come back as an earlier equal object; a `Field(...)` equals only itself, and an `AfterValidator` only one with the same function. With constraints written that way, and a field's own constraints checked as Pydantic holds them, never through a rebuilt `Annotated[...]`, the verdict never depends on which types were evaluated before. To see how a field's own `Annotated[...]` was written, the kernel reads the annotation Pydantic keeps as written (`_original_annotation`, internal to Pydantic, which is pinned to one version; a test fails if it stops being kept). Field validators run in after mode only. A contract has no model validators, serializers, or computed fields of its own, no version 1 validators, no default left unvalidated (`validate_default=False`), no field left out of its written form (`exclude`, `exclude_if`), and no private attributes, and neither it nor a class listed before `Contract` among its bases (a mixin) redefines the kernel's methods (`__init__`, `__setattr__`, `__delattr__`, `__replace__`, `__get_pydantic_core_schema__`, `__get_pydantic_json_schema__` (the committed schema must describe what the contract validates), `model_post_init`, `model_validate`, `model_validate_json`, `model_validate_strings`, `model_dump`, `model_dump_json`, `from_python`, `from_json`, `to_json`, and the base's own check). So input is always read by the declared types first, and values are always written by them. The checks run when the class is created, from the contract's metaclass, after Pydantic has built it: no base class or mixin can skip them (a mixin's own `__pydantic_init_subclass__` included). A later contract that needs something not listed (a mapping, or a union of two contracts, for example) adds it to the kernel's lists, with its tests, as a change to these conventions | Checked when the class is defined (`TypeError`) | `tests/contracts/test_model.py` |
| **Every value has its declared type after validation.** What a validator returns, and every default, is checked against the field's declared type, at any depth: exactly `str`, `int`, `bool`, or `float` (a `bool` is not an `int`), finite floats and amounts, a date that is not a datetime, a tuple of the declared length, an outcome whose value or error has its declared type, and a nested contract whose own fields have theirs (so an instance a validator built without validation is refused too). A validator that returns a float for an amount, or a list for a tuple, is refused, with the error type `contract_value_type` | The base's only model validator, which therefore runs after every field validator | `tests/contracts/test_model.py` |
| **Floats are finite** where a field is a `float` (a value that is not an amount, TEC-003): infinities and NaN are refused, also from JSON (`1e400`, `NaN`) | `allow_inf_nan=False` | `tests/contracts/test_model.py` |
| **Defaults are validated** like any other value | `validate_default` | `tests/contracts/test_model.py` |
| **Amounts are `Amount`**: a `Decimal` built by `atp.numeric.amount` in Python, a string in JSON; a JSON number is refused ([numerical policy](numerical-policy.md), N6). `Amount` is a `type` alias, which cannot be called or subclassed: an alias made by assignment could be, and `Amount("NaN")` would build a `Decimal` without the amount's checks. A constraint on an amount applies however it is written (`q: Amount = Field(gt=0)` or `Annotated[Amount, Field(gt=0)]`): the amount is built first, then Pydantic applies the bounds with its own validators around the amount's schema, and puts `strict=True` into the amount's inner decimal schema. A `multiple_of` check whose whole quotient has more digits than the precision (1E+30 against a multiple of 1E-8: 1E+38 has 39) cannot be computed, so the value is refused as `validator_failed`, with no location. In a contract's committed schema an amount refers to one definition (`"$ref": "#/$defs/Amount"`, the committed `atp.amount` schema without its header), and a bound appears beside the reference under Pydantic's name for it (`"gt": 0`), which is not a JSON Schema keyword: JSON Schema's bounds apply only to numbers, and an amount is a string. The contract enforces the bound | The `Amount` type; a field declared as a plain `Decimal`, or with the amount's own schema (`Annotated[Decimal, AmountSchema]`), is refused when the class is defined | `tests/contracts/test_model.py` |
| **Instances are validated again** wherever a contract is given as input, so an instance built without validation (`model_construct`) cannot pass unchecked. Its validators run again too, as they do when a contract's own JSON is read back: hence the rule on validators below. Pydantic reads an instance by its field names, so an instance of a contract with an alias is refused as input (given to `from_python`, to a constructor, or as a default), while its JSON is read; whether aliases stay allowed, or the kernel reads such an instance under its aliases, is decided at checkpoint C, and no contract uses an alias yet. An instance of a subclass is read as the contract the field declares: one that adds no field comes back as an instance of the declared contract, and one that adds a field is refused (`extra_forbidden`); whether the kernel refuses subclassing a contract that has fields is decided at checkpoint C, and no contract subclasses another yet | `revalidate_instances="always"` | `tests/contracts/test_model.py` |
| **Copying and pickling** keep a contract, its outcomes, and its idempotency keys intact. A contract is not replaced with changed values (`__replace__`, which `copy.replace` calls from Python 3.13): Pydantic's version copies without validating, so a changed contract is validated as a new one | `__reduce__` on the outcome, the key, and `ContractError`; `__replace__` raises `TypeError` | `tests/contracts/test_model.py`, `tests/contracts/test_outcome.py`, `tests/contracts/test_idempotency.py` |
| **Outcomes and idempotency keys** are fields of the types below | Their own validators | `tests/contracts/test_outcome.py`, `tests/contracts/test_idempotency.py` |

## Validating input and reporting a refusal

- **Input from outside the platform is validated only with `from_python(data)` or `from_json(text)`.** `from_python` takes data in the contract's own types, strictly: a tuple, not a list; an enum member, not its value. A parsed TOML document holds lists and plain strings, so it is refused there wherever the contract has a tuple or an enum; how configuration documents reach contracts is settled at checkpoint C ([stage record](../traceability/stage-01-foundation.md)). `from_json` reads arrays and values in their JSON forms. Both raise `ContractError` when the input is refused, including when a validator raises an exception of its own (a `KeyError` from a lookup, for example): that becomes one refusal of type `validator_failed` whose message names only the exception's type, since the exception's text may quote the input. The one exception that propagates is `atp.numeric.DecimalContextError`: a process that never configured its decimal context has a configuration error, not refused input. The structure test fails if, outside `atp.contracts`, anything calls the Pydantic methods that validate without this redaction or skip validation: `model_validate`, `model_validate_json`, `model_validate_strings`, `model_construct`, `model_copy`, a `TypeAdapter`'s `validate_python`, `validate_json`, or `validate_strings`, a model's `__pydantic_validator__` and its `validate_assignment`, the deprecated `construct`, `parse_obj`, `parse_raw`, `parse_file`, `from_orm`, or `copy(update=…)`; or defines a Pydantic model that is not a contract, or uses a Pydantic dataclass, `create_model`, `validate_call`, or `TypeAdapter`. Outside `atp.contracts`, Pydantic is imported only by name and only `Field`, `AfterValidator`, `field_validator`, `ValidationInfo`, and `ValidationError`: no `import pydantic`, nothing from its submodules, nothing from `pydantic_core`, and neither by name through `importlib.import_module` or `__import__` (`atp.contracts` re-exports `PydanticCustomError` for validators). The deprecated `validate` has too common a name to scan and is caught in review.
- **A refusal never carries the input** (SEC-005). No form of Pydantic's validation error is free of the input: its string form leaves out the input values themselves, but its structured forms keep them, its locations keep the name of an unknown field or a mapping key that came from the input, and some of its messages quote the input (a validator's own message, an outcome's unknown tag), the last two in the string form too. `validation_error_details(error)` is therefore the one way to render a validation error:
  - it leaves the input, the context, and the documentation links out;
  - it keeps a location part only if it is a position or a name that some contract declares (a field, an alias, the outcome's tags and fields), and writes `<redacted>` for every other part, the name of an unknown field included; the last part of an unknown-field or invalid-key error is always redacted, since it is a key from the input even when it is a number;
  - it keeps Pydantic's message only for error types whose messages are fixed text or name only facts of the schema (expected types, patterns, limits, allowed values), not counts of the input's items (`too_long` and `too_short` say how many were given), and for the kernel's own error types (`amount_type`, `amount_invalid`, `contract_value_type`, `idempotency_key_type`, `idempotency_key_invalid`), whose messages are fixed text (an amount's are `atp.numeric.AMOUNT_REFUSALS`); and even for those types only when the message is the type's own: the one Pydantic gives for that type and its context, for Python or JSON input, or one of the kernel's fixed texts, registered by the module that raises it. Any other message gets `invalid value`. That covers `value_error`, whose message is whatever a validator wrote, and a validator that raises one of the listed types with a message of its own, so a later validator that quoted its input could not leak it.
- **`ContractError`** is a `ValueError` holding the contract's identity and the redacted details only. Its text lists one refusal per line; `to_json()` gives the same for structured logs. It holds no reference to the original Pydantic error: it is raised after the handler that caught that error has finished, so neither its `__cause__` nor its `__context__` leads back to the input.
- **A contract built in code with keyword arguments** (`Leg(price=…, venue=…)`) raises Pydantic's own error for a wrong value, because that is a programming error, not refused input; a validator's own exception propagates from it unchanged. Its string form can show input (the bullet above): an unknown keyword's name, a validator's own message, an outcome's unknown tag. So data from outside the platform never goes through the constructor (`X(**data)`), and a validation error is rendered only through `validation_error_details`, never with `str`, `repr`, or by logging the exception. No check enforces either rule: the structure test finds Pydantic's own validation methods outside `atp.contracts`, not a constructor given outside data, nor how an error is rendered, so both are caught only in review.
- **Validators** written in later contracts are field validators in after mode or `AfterValidator`s: they receive values already validated strictly, and what they return is checked against the field's type. A validator checks: it returns the value it was given, unchanged, or raises. It neither converts nor normalizes: every instance given as input, and a contract's own JSON read back, is validated again, so a conversion (a percentage to a fraction) would be applied again each time, silently; and a constraint written before a validator is checked on the value the validator was given, not on the one it returns, so a normalization (a quantity rounded down to a step with `quantize`) could store 0 in a field declared greater than 0, which the contract would then refuse as its own input. Conversions and normalizations belong in the code that builds the input. No check enforces this, so it is caught only in review; tests show both hazards, and whether the kernel should refuse a validator's result that differs from its input is decided at checkpoint C. A cross-field check is an after-mode field validator that takes `info: ValidationInfo` and reads an earlier field with `info.data.get(name)`: a field that failed validation is absent there, and `info.data[name]` would raise. They raise with fixed text or with their own error types (`PydanticCustomError`, imported from `atp.contracts`), never with the value in the message; a validator's own error type is kept in the refusal, its message is not; a plain `ValueError`'s or `assert`'s message is replaced by `invalid value` anyway, and so is the message of a validator that reuses a listed type. A validator that gave one of Pydantic's types a context built from its input, which that type's own message would then show, is caught only in review.
- **`to_json()` is the one writer** of a contract's written form. `model_dump_json` or `model_dump` called with options of its own (`by_alias=False`, `exclude`, `exclude_none`) would write another form, which a reader may refuse or read differently; that is caught only in review.
- **Two limits outside the refusal itself.** A traceback's frames still hold the input in their local variables (for example `from_python`'s `data`), so a tool that records frame variables would record it; the observability stage must not capture them for refusals. And JSON with a repeated key is read with the last value winning, as Python's JSON parser does.

Tests: `tests/contracts/test_model.py` gives a secret-like value as a field value, as an unknown key, as a nested unknown key, as an outcome's tag, in a validator's message, and as an assigned value, and checks that the error's text, its JSON, its details, and captured log output never contain it, and that the refusal has no `__cause__` or `__context__`.

## Versions and compatibility (ARCH-026, GOV-006)

- **A version is `MAJOR.MINOR`** (`ContractVersion`), with no leading zeros; a contract's first version is `1.0`.
- **A new minor version** may only add: a field with a default that keeps the meaning of data written without it, or a further allowed value. Everything valid under the earlier minor version stays valid, with the same meaning.
- **A new major version** is needed for every other change: removing or renaming a field, changing a type, a default, or a meaning, making a field required, or narrowing what is allowed.
- **Compatibility:** `is_compatible(produced, understood)` is true only when the major versions are equal and the data's minor version is not later than the reader's. Different major versions are never compatible. A reader cannot accept data of a later minor version, because that data may carry a field it would refuse.
- **How data names its contract and version** in transit or storage (an envelope field, a message header) is decided with the first messaging and storage, in DATA FOUNDATION.

Tests: `tests/contracts/test_version.py`.

## Committed schemas (GOV-006, GOV-007)

- **Location:** `contracts/<contract identity>/<MAJOR.MINOR>.schema.json`, one file per contract version. The schema uses JSON Schema draft 2020-12; its `$id` is `<identity>/<version>` and its title is the identity. It is generated by Pydantic for validation and written with sorted keys, two-space indentation, and a final newline.
- **The pattern in the amount schema** is anchored with `^` and `$`. JSON Schema reads them as in ECMAScript, where `$` is the end of the text; a validator built on Python's `re` would also accept a final line break, which the code refuses.
- **Which schemas:** the kernel's three types, each with its own identity at version 1.0 (`atp.amount`, `atp.idempotency-key`, `atp.outcome`), and every contract defined in the platform's own modules: every module of the `atp` package is imported first, so a contract in a module nothing else imports is not missed. Contracts defined in tests have none.
- **A schema never changes without a new version.** The tests compare the committed file of each contract's current version with the schema the code produces; any difference fails, and the message asks for a new version. Every committed file must belong to a known contract. Files of earlier versions stay committed as the record of what that version's data looked like.
- **Adding a version's file:** `write_schema_files(directory)` writes the file of each version not yet committed and refuses to overwrite a committed version with different content. The command is in the [developer guide](../development.md).

Tests: `tests/contracts/test_schemas.py`.

## Outcomes (ARCH-042)

`Outcome[ValueType, ErrorType]` is the result of one external operation: SUCCESS with a value, FAILURE with an error, TIMEOUT, or UNKNOWN.

| Property | How |
|---|---|
| **No default in a contract, yet.** A field of an outcome type with a default (`= Outcome.unknown()`) makes JSON input without that field refused and its schema impossible to produce; `Outcome[...] \| None = None` works. Whether such defaults are refused when the class is defined, or supported, is decided at checkpoint C | Recorded; no contract holds one |
| **Built only through its four constructors** | `Outcome.success(value)`, `Outcome.failure(error)`, `Outcome.timeout()`, `Outcome.unknown()`; calling the class directly is refused, and the class cannot be subclassed |
| **Read only through `fold`**, which needs a handler for each result | `fold(on_success=…, on_failure=…, on_timeout=…, on_unknown=…)`; leaving one out is a type error, so UNKNOWN can never be read as SUCCESS by omission |
| **No truth value** | Using an outcome as a truth value raises `TypeError`. In `if`, `while`, `not`, `and`, `or`, and `assert` it is also a type error (mypy's `truthy-bool`): the method that raises is hidden from the type checker on purpose, because mypy would stop reporting if it saw one. An explicit `bool(outcome)` is caught only when it runs |
| **No comparison** | `==` raises, because it would test the result outside `fold`; an outcome is not hashable. So a contract that holds an outcome cannot be compared with `==` or hashed either |
| **Private kind and value** | They are kept in private slots. ruff's private-member rule (SLF001) and the structure test refuse code that reads them by name outside `atp.contracts`, and no module may import `atp.contracts`' private modules. Python's introspection can still reach them (`object.__getattribute__`, the state used for pickling), `repr` names the result for diagnostics, and the JSON form (`to_json()`, `model_dump(mode="json")`) shows it, as a message must; code that reads the result from any of these instead of using `fold` is caught in review |
| **Immutable** | Assignment raises |
| **In a contract** | The value and error must have the types the field declares, strictly, also when an `Outcome` instance is given: the instance is checked through its envelope. A Python dump (`model_dump()`) keeps the outcome object |
| **In JSON** | `{"result": "SUCCESS", "value": …}`, `{"result": "FAILURE", "error": …}`, `{"result": "TIMEOUT"}`, `{"result": "UNKNOWN"}`; any other result or field is refused |

States particular to one operation, such as a transfer's "pending" (EXE-009), belong to that operation's own contract, written in its stage; they are never mapped to SUCCESS unless the operation is confirmed complete.

Tests: `tests/contracts/test_outcome.py`. The type errors are kept by `tests/contracts/type_checks.py`, which pytest does not run and strict mypy checks: each line that must not type-check is marked with an ignore comment naming its error code, and strict mypy reports an ignore that no longer silences anything, so the type check fails if one of those errors ever disappears. `tests/contracts/test_type_checks.py` checks that the lines are still there.

## Idempotency keys (ARCH-041)

`IdempotencyKey` is a request's identity: retrying a request with the same key must not repeat the operation. It is 32 lowercase hexadecimal characters (128 bits); `IdempotencyKey.new()` draws one from the operating system's secure random source (`secrets`). It is immutable, cannot be subclassed, equal to another key with the same text, usable as a dictionary key, and a string in JSON. A key field reads a key, or its text, in Python input as in JSON, as an amount field reads an amount's text: the text is checked the same way, and anything else (another type, a subclass of `str`) is refused. A key in a default would be shared by every instance built without it, so two operations would carry one key, and validating a default turns a key's text into a key: a field whose type can hold a key (the key itself, or a union, tuple, frozenset, outcome, or contract that can) takes its default from a factory (`Field(default_factory=IdempotencyKey.new)`), or has `None` or an empty tuple or frozenset as its default, and any other default is refused when the class is defined. A factory that returns the same key each time is caught only in review. A key stands in a union only beside `None` ([Writing a contract](#writing-a-contract)). Making an operation idempotent with it belongs to that operation's own contract, written in its stage (CORE TRADING FOUNDATION and later).
