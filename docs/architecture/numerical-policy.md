# Numerical Policy

> **Status:** ACTIVE — the rules for financial amounts in the code, approved by the owner as decision D7 of the [Stage 1 plan](../roadmap/stage-01-foundation-plan.md) ([DEC-038](../decisions/DEC-038-stage-1-plan-approved.md)) and built at Stage 1's checkpoint B (U2), 2026-10-07 · **Owner:** platform architecture, cross-cutting ([architecture-to-repository map](source-of-truth-map.md#architecture-to-repository)) · **Requirements:** ARCH-010 and ARCH-011 ([architecture overview](overview.md)), TEC-003 ([technology stack](technology-stack.md)); the precision is V-40 in the [values register](../requirements/values-register.md) (ARCH-018)
>
> How the code makes exact decimal arithmetic enforceable by code and tests, not only by review. The requirements' text stays in their owning specifications; this document says how the code meets them. Code: `src/atp/numeric/`. Tests: `tests/numeric/` and the structure test `tests/repository/test_structure.py`. Every system that handles an amount uses this module (master execution constitution §30); none reimplements it.

## Rules

| # | Rule | How the code enforces it | Tests |
|---|---|---|---|
| N1 | **One constructor.** Every amount is built with `atp.numeric.amount(value)` | It accepts exactly `str`, `int`, and `Decimal`; a `bool`, a float, any other type, and subclasses of the three are refused (`TypeError`). Text must have the form `AMOUNT_PATTERN`: ASCII digits with an optional sign, point, and exponent; no spaces, digit separators, other scripts' digits, NaN, or infinity. NaN and infinities given as `Decimal` are refused, as are more significant digits than the precision and an exponent outside the context's range, including one too large for Python's decimal module itself (`AmountError`), so an amount that could not be computed with exactly is refused when it enters, not later inside arithmetic. A refusal's message never contains the refused value | `tests/numeric/test_amount.py` |
| N2 | **No amount built, and no context changed, outside `atp.numeric`;** the ways a float becomes an amount are refused anywhere | The structure test reads `src/` with `ast`. Outside `atp.numeric` it fails on: any reference to `Decimal` (under any name, through any module: `fractions.Decimal` is the same class) that is not a type use, so a call, but also `Decimal` handed on as a converter, stored, returned, or bound to another name. `Decimal`, and what stands for it (`Annotated[Decimal, ...]`, also imported under another name, and a one-member `Union[Decimal]`, which is `Decimal` itself: calling or subclassing either calls or subclasses `Decimal`), are type uses only as an `is` comparison, a `case Decimal()` pattern, a type hint, the value of a `type` statement, an `isinstance` or `issubclass` check, `cast`'s or `NewType`'s type, or a type variable's bound or constraint; anywhere else they are findings: called, subclassed, handed on, or assigned to a name, which could then be called (`Kind = Annotated[Decimal, ...]`; a `type` statement, `type Kind = ...`, makes an alias that cannot be called, which is why `Amount` is one, N6). Inside another type (`dict[str, Decimal]`, `Callable[[Decimal], None]`, `Decimal \| None`) `Decimal` is a type use anywhere, since that type builds no `Decimal`; in `Annotated`'s metadata it is a value; and a call is never a type use, even inside brackets (`Annotated[Decimal, Field(gt=Decimal("0"))]` builds an amount); a star import from `decimal`; calling a value's own type (`type(x)(…)`, `x.__class__(…)`); any use of the decimal context (`getcontext`, `setcontext`, `localcontext`, `Context`, and the predefined contexts, reached through `decimal`; `create_decimal` and `traps` on any object), which could untrap `Inexact`. Outside `atp.contracts` it fails on the Pydantic constructs that would build a `Decimal` from a float without the contract kernel's rules: a model that is not a contract, a Pydantic dataclass in any spelling, `create_model`, `validate_call`, a `TypeAdapter`; there Pydantic is imported only by name, and only `Field`, `AfterValidator`, `field_validator`, `ValidationInfo`, and `ValidationError` (nothing from its submodules or from `pydantic_core`, and neither by name through `importlib.import_module`, under any name, or `__import__`). Inside, the kernel refuses any contract that could read input before its declared types do ([contract conventions](contracts.md)). Anywhere in `src/`, `atp.numeric` included, it fails on `Decimal.from_float`, `create_decimal_from_float`, reading TOML (N7) without `parse_float`, reading JSON (`json.load`, `json.loads`, `JSONDecoder` however reached or imported) without both `parse_float` and `parse_constant` (JSON's `NaN`, `Infinity`, and `-Infinity` reach `parse_constant`, never `parse_float`; `amount` refuses them there too), `ast.literal_eval` (it reads `0.1` as a float), and an amount built from a value's text: `str()`, `repr()`, `ascii()`, `format()`, an f-string with a replacement field, `.format()`, `json.dumps()`, `__str__()`, `__repr__()`, `__format__()`, `locale.str()`, `locale.format_string()`, `locale.currency()` (`locale.str` also rounds a float to 12 digits), or `%` formatting anywhere in an argument of `amount()` or `amount_from_toml()`, under any name they are imported as; `None` given for `parse_float` or `parse_constant` counts as leaving it out (a float's text holds its binary error: `str(1 / 3)` is `0.3333333333333333`). Every scanner is run on planted samples too, so one that stopped finding anything would fail | `tests/repository/test_structure.py` |
| N3 | **One decimal context, set once at process start** | `configure_decimal_context()` sets the fields of `decimal.DefaultContext` and of the current context in place (rebinding the name `DefaultContext` would not reach new threads): precision 34 (V-40); traps `FloatOperation`, `InvalidOperation`, `DivisionByZero`, `Overflow`, and `Inexact`; every other signal only recorded as a flag; exponent range ±999,999 (Python's default); exponents written with a capital `E` (`capitals`, Python's default); no clamping. New threads start from `DefaultContext`; new asyncio tasks copy the current context. `amount()` and `quantize()` raise `DecimalContextError` (a `RuntimeError`) if the current context is not the configured one, so a process that forgot to configure it fails at its first amount; a contract's `from_python` and `from_json` let it propagate, since it is a configuration error, not refused input. The test session configures it in `tests/conftest.py`, as a process would at start | `tests/numeric/test_context.py` |
| N4 | **No silent rounding** | `Inexact` is trapped, so an arithmetic operation whose exact result does not fit the precision raises instead of rounding (1 / 3 raises; 1 / 4 gives 0.25). Some operations round to a whole number, or convert, without signalling: `round()` (called or referenced, also as `builtins.round`), `to_integral`, `to_integral_value`, the rounding methods `__round__`, `__floor__`, `__ceil__`, `__trunc__`, `__int__` (it truncates, as `int()` does), `__float__`, `float`, and `complex` (0.1 becomes a binary approximation), also reached as `builtins.float` or imported from `builtins` under another name, and any attribute of `float` or `complex` (`float.fromhex` builds a float), the `math`, `cmath`, and `statistics` modules (they compute in floats or round: `math.floor`, `math.sqrt`, `math.isclose`, `statistics.fmean`), and integer division, remainder, and `divmod`, also through their dunders (`__floordiv__`, `__mod__`, `__divmod__`, and the reflected ones), the `operator` module's `floordiv` and `mod` (also by their dunder names), `divmod` reached as an attribute (`builtins.divmod`), a decimal context's `divide_int`, and `remainder_near` (`p - p.remainder_near(tick)` rounds to the nearest tick) (`amount("-2.7") // amount("1")` is -2: they truncate toward zero, so `x // tick * tick` is wrong for negative values). The structure test refuses them anywhere in `src/`: importing one of the three modules is the finding, and `%` is refused as formatting too. The exceptions are the modules it lists as allowed to use floats (TEC-003 allows floats for indicators, signals, and research), of which there are none in Stage 1, and `divmod` in `atp.numeric._rounding`, which N5 uses exactly. A module that divides only integers (timestamps into intervals, counts) gets its entry in the structure test's `INTEGER_DIVISION_ALLOWED`, and one that needs floats its entry in `FLOAT_ALLOWED`, each by a reviewed change whose tests show it never divides or converts an amount. Naming `float` in a type hint, a type check, or a tuple of types is not a finding. `int()` (which truncates), formatting a value to fewer places (`format`, f-strings), `Decimal.shift` and `rotate`, and dividing two integers (`/` gives a float) are caught only in review ("What the rules do not catch") | `tests/numeric/test_context.py`; `tests/repository/test_structure.py` |
| N5 | **Rounding only on request, with a named direction** | `quantize(value, increment, rounding)` rounds to a multiple of an increment (a tick or step size, ARCH-011) in one of four directions: `TOWARD_ZERO`, `AWAY_FROM_ZERO`, `TOWARD_NEGATIVE_INFINITY`, `TOWARD_POSITIVE_INFINITY` (the meanings of `decimal`'s `ROUND_DOWN`, `ROUND_UP`, `ROUND_FLOOR`, `ROUND_CEILING`), so the result is defined for negative values too. Every step is exact: the integer quotient and remainder come from `divmod`, never from a rounded division (at 34 digits, 9.899…9 rounded down to a multiple of 0.3 gives 9.6, where a rounded quotient would give 9.9). No step untraps `Inexact`; a step that would need more digits than the precision raises: the result, or the whole-number quotient (so 1E+40 rounded to a multiple of 1 raises, although the result itself would fit). The result is a multiple of the increment, written with the increment's exponent unless the precision makes trailing zeros be dropped (the value is the same); it is less than one increment from the value, equal to it when the value already is a multiple, and an unsigned zero when it is zero. A zero or negative increment, a non-finite operand, and an operand that is not a `Decimal` are refused | `tests/numeric/test_rounding.py` (properties for both signs, including at full precision next to an increment boundary; the 9.6 example) |
| N6 | **Amounts in JSON are strings** | The contract field type `Amount` ([contract conventions](contracts.md)) accepts a string or, from Python code, a `Decimal`. It is a `type` alias, which cannot be called or subclassed, so it builds no amount itself; a JSON number, integer or not, is refused, and the committed schema `contracts/atp.amount/1.0.schema.json` says so (type string, the pattern of N1). A contract cannot change that: a validator that reads input before `Amount` does, a serializer, an unvalidated default, a setting such as `json_encoders`, and a union of an amount, with or without constraints or validators of its own, also one written inside metadata (`Annotated[Amount \| None, Field(gt=0)] \| float`), with anything but `None` or a literal of strings are refused when it is defined, and a value that is not a finite `Decimal` after validation is refused (`contract_value_type`). A constraint on an amount applies however it is written, and its bound is an amount or an integer, never a float, text, or a bool | `tests/contracts/test_model.py`, `tests/contracts/test_schemas.py` |
| N7 | **Amounts in TOML go through the constructor** | TOML text is read with `tomllib.loads(text, parse_float=amount_from_toml)`: every TOML float becomes a `Decimal` built by N1, so no float is produced; the structure test refuses a `tomllib.load` or `loads` in `src/` without `parse_float`. TOML allows underscores between digits; `amount_from_toml` removes every underscore first, so it is meant only as `parse_float`, where TOML's grammar has already checked their places. TOML's `inf` and `nan` are refused. A configuration file is then validated in its JSON form, so an amount in it is written as a string, as in JSON (N6), and a TOML number given for an amount is refused, integer or not (`atp.config`; the [developer guide](../development.md), "Configuration") | `tests/numeric/test_amount.py`; `tests/repository/test_structure.py`; `tests/config/test_load.py` |
| N8 | **Property tests use exact decimal strategies** | Hypothesis's decimal strategies are always given `places=`; with `Inexact` trapped, limits alone still raise | The tests of `tests/numeric/` |

The tests also pin the rules themselves: the five trapped signals are listed literally; a context that differs from the platform's in any field or trap is not "configured"; division by zero and overflow raise; the exponent range is tested at both of its limits; every rule above was shown to have a test that fails without it (Stage 1 checkpoint B's [verification record](../traceability/stage-01-checkpoint-b-verification.md), check 7); and every entry of the structure test's lists of names has a planted sample of its own, so removing an entry fails a test.

## The precision (V-40)

34 significant digits, an IMPLEMENTATION CHOICE (ARCH-018). It is the significand of IEEE 754's decimal128 format, a standard width. The product of two amounts of up to 17 significant digits each is exact; a result that does not fit raises `Inexact` (N4) rather than being rounded. Changing it is a change to this policy, to V-40, and to the tests that use `PRECISION`.

## What the rules do not catch

- **Equality between an amount and a float** (`price == 0.5`) neither raises nor fails the type check: Python's `FloatOperation` trap leaves equality comparisons silent by design, and strict mypy accepts the comparison (checked with mypy 2.4.0 on 2026-10-07). The constructor refuses a float (N1), but a comparison with one is caught only in review. Stage 1's code contains no float.
- **A float that became text elsewhere.** `amount()` accepts text, and a float's text holds its binary error (`str(0.1 + 0.2)` is `0.30000000000000004`). The scanner finds text made from a value inside the call to `amount()` itself, in the spellings N2 lists; text made there in other ways (`"{x}".format_map(…)`, `string.Template("$x").substitute(…)`, `"".join(map(str, …))`), text made earlier and passed along, text given straight to a contract's amount field (`Leg(price=str(x))`, which the field accepts as text), and a float produced by dividing two integers (`/`), are caught only in review. Stage 1's code contains no float.
- **A `Decimal` given to a contract's float field** is read as the nearest float, without an error: Pydantic's strict mode accepts it there. A float field holds only values that are not amounts (TEC-003), so an amount given to one is caught only in review ([contract conventions](contracts.md)); whether a float field refuses a `Decimal` is decided at checkpoint C.
- **`int()` and formatting round silently.** `int(amount)` truncates toward zero, and `format(amount, ".1f")` or an f-string with fewer places rounds half-even, without any signal. The scanner cannot tell an amount from an ordinary number there, so these are caught only in review; code that needs a whole number or fewer places uses `quantize` with a named direction.
- **`Decimal.shift` and `rotate`** move digits without signalling; nothing in the platform needs them, and their use is caught only in review.
- **The scanners read names.** Code that reaches `Decimal`, `float`, or a rounding function only dynamically (`getattr`, `importlib`, `eval`), through a type alias's value (`Amount.__value__`, `typing.get_args`), or keeps `float` in a list or tuple and calls it from there, is caught only in review. So is a JSON or TOML reader, an amount builder, `Annotated`, or a value's own type, reached through a variable it was assigned to (`loads = json.loads` then `loads(text)`; `build = amount` then `build(str(x))`; `kind = type(value)` then `kind(text)`), and a subclass of `JSONDecoder`; assigning `Decimal` or `float` to a variable is itself a finding.
- **Ordinary code the rules refuse, and what to write instead.** `type(x) == Decimal` is refused (an `==` comparison is not a type use): write `type(x) is Decimal` or `isinstance`, as ruff's E721 also asks. A `functools.singledispatch` overload for `Decimal` is registered by its annotation (`@f.register` over `def _(value: Decimal)`), not by `f.register(Decimal)`, which hands `Decimal` on. An exchange's integer precision becomes a tick size with `amount(1).scaleb(-precision)`, which is exact, not with text built from it (`amount(f"1e-{precision}")` builds an amount from a value's text).
- **A decimal context's `remainder`** truncates as `%` does. Outside `atp.numeric`, obtaining the context is itself a finding (N2); inside it, the context's use is caught in review.
- **Tests may build `Decimal` directly,** for example to state an expected value; the structure test reads `src/` only.
- **Division with a named direction is not provided yet.** Stage 1 has no calculation that needs a rounded quotient. The first stage that needs one (position sizing, for example) adds it to `atp.numeric` under N4 and N5, with its tests; until then any inexact division raises.
- **The increments themselves** (each venue's tick and step sizes) come from DATA FOUNDATION, which completes ARCH-011 ([Stage 1 plan](../roadmap/stage-01-foundation-plan.md), section 3.2).
