PERMANENT DIRECTIVE — FASTER DEVELOPMENT, LOWER TOKEN CONSUMPTION & UNCHANGED COMPANY-GRADE QUALITY
SERIOUS MODE — MANDATORY
Claude Code, I am concerned about the rate at which you consume tokens and how slowly meaningful development is progressing.
I want you to improve development efficiency substantially without weakening anything important or introducing new problems.
PRIMARY OBJECTIVE
Achieve the highest practical development efficiency while maintaining the full integrity, correctness, security, safety, traceability, maintainability, and long-term reliability of this company-grade autonomous trading platform.
This is not permission to rush, skip verification, remove important functionality, or compromise engineering standards.
1. AUDIT THE REAL CAUSES OF TOKEN WASTE
Before changing the development process, inspect the existing project rules and recent development activity.
Identify where excessive tokens, time, and unnecessary work are being consumed.
Pay particular attention to:

* Repeatedly reading large unchanged documentation.
* Repeatedly analyzing completed work.
* Excessive context loading.
* Unnecessary independent-review cycles.
* Repeated Gate 3 failures caused by preventable documentation mistakes.
* Duplicated documentation and reporting.
* Repeated testing without technical justification.
* Unnecessary creation of files, decisions, or governance records.
* Excessive reasoning for straightforward tasks.
* Repeated GitHub and backup operations.
* Work that deterministic scripts can perform instead of AI.

Do not assume the cause. Identify it using available evidence.
2. OPTIMIZE THE EXISTING SYSTEM — DO NOT DUPLICATE IT
Search the repository for existing token-efficiency, model-routing, anti-loop, convergence, verification, and development-continuity controls.
If they already exist, enhance and enforce them.
Do not create another competing optimization system, duplicate rule set, or source of truth.
Preserve all previously approved decisions.
3. USE INTELLIGENCE ACCORDING TO TASK COMPLEXITY
Use the most suitable available model and tools for each task.
Prefer inexpensive, efficient methods for routine operations.
Reserve stronger reasoning for tasks requiring it, especially:

* Complex architecture decisions.
* Financial correctness.
* Security and risk analysis.
* Root-cause investigation.
* Significant integration decisions.
* Ambiguous requirements.
* Independent verification.

Use deterministic tools for searching, indexing, formatting, generating reports, testing, and checking repository consistency wherever suitable.
Never choose a cheaper or faster method when doing so materially increases engineering risk.
4. REDUCE UNNECESSARY CONTEXT
At each session start, recover the current project state from the existing canonical continuation records.
Load only the files relevant to the active task and its dependencies.
Do not repeatedly read the entire repository, all historical decisions, or every previous verification report unless the task genuinely requires it.
Use targeted search, repository indexes, and approved repository-intelligence tools where appropriate.
Preserve full requirements and decisions in the repository. Optimize what is loaded into active AI context, not what is permanently stored.
5. MAKE VERIFICATION MORE EFFICIENT WITHOUT WEAKENING IT
Keep all three mandatory verification gates.
Before expensive independent reviews:

1. Complete the authorized implementation.
2. Run deterministic checks.
3. Resolve known findings.
4. Check documentation and traceability.
5. Confirm the candidate is internally consistent.
6. Present the stable candidate for independent verification.

If verification finds problems, investigate common root causes, correct related findings together when appropriate, and revalidate according to impact.
Reuse valid existing evidence only when technically and procedurally permitted.
Never bypass a required gate or claim a failed gate passed merely to save tokens.
6. STOP UNNECESSARY REPETITION AND LOOPS
If the same problem repeatedly occurs, investigate why previous corrections did not resolve it.
Do not repeat the same unsuccessful process indefinitely.
Distinguish real defects from optional improvements and future-stage work.
Keep current-stage exit criteria stable.
Correct genuine blockers, but do not continually expand the current stage with unnecessary enhancements.
7. PRESERVE ALL IMPORTANT WORK
Token optimization must never cause important work to be lost.
Maintain the approved repository checkpoint, temporary backup, reconciliation, and recovery mechanisms.
The platform must remain recoverable after a session interruption or months of inactivity.
Avoid redundant backup operations and unnecessary CI noise, but preserve the required safety checks and all verification obligations before authoritative promotion.
8. PRIORITIZE MEANINGFUL ENGINEERING PROGRESS
Focus development resources on completing the current authorized stage and its actual required deliverables.
Do not confuse creating more documentation, running more reviews, or consuming more tokens with real project progress.
Measure progress using:

* Completed approved deliverables.
* Resolved legitimate blockers.
* Successful required verification.
* Reduced remaining work.
* Stable verified checkpoints.
* Authorized stage progression.

Do not reopen completed Stage 1 work without a genuine technical or governance reason.
9. REDUCE UNNECESSARY RESPONSES
During normal work, communicate concisely.
Report meaningful progress, significant findings, blockers, decisions requiring my approval, and verification results.
Do not repeatedly explain the entire project or reproduce long documents in conversational responses.
Keep full material evidence in its correct canonical repository location.

These optimizations must never weaken:

* Deterministic trading logic.
* Capital Authority.
* Risk Engine.
* Execution Engine.
* Financial precision and accounting.
* Exchange reconciliation.
* Security and credential protection.
* Data integrity.
* Recovery and failover.
* AI authority restrictions.
* Monitoring and auditability.
* Required testing.
* Independent verification.
* Change governance.

Speed improvements must be assessed for their effect on correctness, safety, and maintainability.

Use the smallest effective improvement to the existing development process.
Do not introduce elaborate orchestration, unnecessary AI agents, new frameworks, or competing workflows solely for token reduction.

B. Main verified or reasonably evidenced sources of wasted tokens.
C. Existing optimization mechanisms already available.
D. Improvements that can be applied immediately within existing authority.
E. Any changes requiring my approval.
F. How all original quality and verification controls remain protected.

H. Exact next authorized development action.

I want Claude Code to become substantially more efficient, not less intelligent or less careful.

Do not waste expensive reasoning on repetitive work.
Do not create duplicates.
