## U7: the verification matrix

**Design** (the plan's U7 and its decision D10: markers in module docstrings and pytest markers, and a generated matrix). The forms, and how to write them, are in the [documentation tools](../../tools/docs/README.md#requirement-markers-and-the-verification-matrix):

- A paragraph that begins `Requirements:` names what an artifact implements: in a module's docstring under `src/` or `tools/`, a `#` comment of `pyproject.toml` or a workflow, or an HTML comment of a document under `docs/` (the threat model and the developer guide, for SEC-001 and GOV-023, whose implementation is not a module). A paragraph that begins `Verifies:`, read only in a module under `tools/` or a document under `docs/traceability/` (the tools, and the verification records), names what a check that is not a pytest test verifies: the documentation tools' self-test (ARCH-032 and the traceability requirements), Gate 3's review of the threat model in checkpoint C's record (SEC-001), the machine checks' recorded runs in the stage record (GOV-023, GOV-012), and this record's run from a clean clone, check 7 (GOV-023), whose commands the stage record lists. `@pytest.mark.req("ID", ...)`, on one line above a test function at module level, in a test module (`test_*.py` or `*_test.py`), where pytest collects it, names what the test verifies.
- The markers are read as text, so the tools still run on Python 3.10 while the code is Python 3.12. A marker names the IDs outside parentheses, so a parenthesis can explain without marking; decision IDs are never marked.
- The matrix has the columns of the plan's U7 and of §145: requirement (linked to its specification), what Stage 1 delivers of it (the plan's section 3.1, with its row's note where it has one), owning system and default stage (the registry's, repeated), system rule (the System Rules Register), interface (the committed contracts defined by a package that implements it), implementation, tests and checks, verification (the checkpoint that built each unit the plan assigns it, with its record, where the evidence is), and status, which is that of what Stage 1 delivers, not of the whole requirement: no requirement is yet implemented in full (the [requirements README](../requirements/README.md), "Status"). The commit is that record's row of the project state's checkpoint log, since a generated file cannot hold its own commit. Its banner states how each link of owner decisions 14's §31 chain is reached, from its columns or the registry's, without a second registry (the stage record's "Carried to checkpoint D").
- The matrix's second table lists the other requirements a marker names, each with the disposition the plan's section 3 gives it; its third lists every test module with its number of test functions and how many name a requirement, so a test without a requirement is visible, as U7's purpose asks, by module. A test that names none still runs at every checkpoint and on every push.

**What the checker now refuses** (each check with its mutation, and each with its self-test case, but for the class no requirement has): a marker that names no requirement; a marker that names an unknown requirement, or one that is not approved (PROPOSED, FUTURE, PREVIOUSLY DISCUSSED / REQUIRES CONFIRMATION, or DEPRECATED / REPLACED: ARCH-029, GOV-017; one check, with a self-test case for each class a requirement has: no requirement is PREVIOUSLY DISCUSSED / REQUIRES CONFIRMATION); a `req` marker that takes anything other than requirement IDs written as strings, does not decorate a test function at module level (on a test nested in another, or a method of a class), is in a module pytest collects no tests from, or is not written on one line as a decorator; a `Verifies:` marker outside `tools/` and `docs/traceability/`; a requirement of the plan's section 3.1 without an implementation marker, or without a test or check marker; a unit of section 3.1 in no checkpoint of the stage record; the plan's section 3.1 not found under its heading, which would leave the checks of section 3.1 nothing to check; and a matrix out of date, edited by hand or left behind by a change. The self-test also has cases that must pass, one for each rule that keeps text from being read as a marker: a requirement named inside a marker's parenthesis, or after its first sentence; a decision named in a marker; a marker inside a code block; and a `req` marker above another decorator written on several lines. The rule that generated files are not read for markers changes nothing a check can see: no generated file holds a marker, and a hand edit of one is refused as stale; Gate 3 run 1 removed it and nothing changed.

**What the checker does not catch:** a skipped test, or one expected to fail, still counts as a test (pytest's `xfail_strict` fails an expected failure that passes, but nothing reports a skip), and so does a test pytest is told not to collect (`__test__ = False`, a conftest's `collect_ignore`, an option that deselects it), since the checker reads the tests as text and does not run pytest; a `req` marker written otherwise than on one line (`@pytest.mark .req(...)`, a line continued with a backslash) is not read, so the test counts as naming nothing, until `ruff format`, whose check fails meanwhile, writes it on one line; the matrix's last table counts the functions named `test_…` at module level, the only ones a marker can name, so a test pytest collects under another name (`testfoo`) or as a method of a class would run uncounted (the tests have none); a `Verifies:` marker in a module under `tools/` or a document under `docs/traceability/` is taken at its word; and a marker says what its author read the artifact or the test to do: Gate 3 reads each marked test against its requirement (the [documentation tools](../../tools/docs/README.md#requirement-markers-and-the-verification-matrix)).

**Which tests are marked.** For each requirement of section 3.1, the builder marked the tests whose assertions exercise what the requirement asks, read from each test's body: for example, for TEC-003, the tests that a float is refused, that string round trips are exact, and that an inexact result raises; for ARCH-042, the tests that there are exactly four results, that `fold` calls each handler, and that an outcome has no truth value, and the test that the type-test lines are still there, which proves it with the strict type check, which reports a `type: ignore` that is no longer needed. A test that checks only a detail of a module's own rules names nothing. Read so, the two tests first marked for ARCH-018 compared the code's values with numbers written in the tests, not with the values register that ARCH-018 is about: a new test reads V-40 and V-41 from the register and compares them with the code, and those two now name only what they prove. After Gate 3 run 1 (D-03, D-09), ARCH-025 rests on that test alone: the tests that an unknown field is refused and that a contract is immutable check the kernel's own conventions, so they no longer name it.
