## U7: the verification matrix

**Design** (the plan's U7 and its decision D10: markers in module docstrings and pytest markers, and a generated matrix). The forms, and how to write them, are in the [documentation tools](../../tools/docs/README.md#requirement-markers-and-the-verification-matrix):

- A paragraph that begins `Requirements:` names what an artifact implements: in a module's docstring under `src/` or `tools/`, a `#` comment of `pyproject.toml` or a workflow, or an HTML comment of a document under `docs/` (the threat model and the developer guide, for SEC-001 and GOV-023, whose implementation is not a module). A paragraph that begins `Verifies:` names what a check that is not a pytest test verifies: the documentation tools' self-test (ARCH-032 and the traceability requirements), Gate 3's review of the threat model in checkpoint C's record (SEC-001), and the machine checks' recorded runs and the clean-clone run in the stage record (GOV-023, GOV-012). `@pytest.mark.req("ID", ...)`, on one line above a test function, names what the test verifies.
- The markers are read as text, so the tools still run on Python 3.10 while the code is Python 3.12. A marker names the IDs outside parentheses, so a parenthesis can explain without marking; decision IDs are never marked.
- The matrix has the columns of the plan's U7 and of §145: requirement (linked to its specification), what Stage 1 delivers of it (the plan's section 3.1, with its row's note where it has one), owning system and default stage (the registry's, repeated), system rule (the System Rules Register), interface (the committed contracts defined by a package that implements it), implementation, tests and checks, verification (the checkpoint that built each unit the plan assigns it, with its record, where the evidence is), and status, which is that of what Stage 1 delivers, not of the whole requirement: no requirement is yet implemented in full (the [requirements README](../requirements/README.md), "Status"). The commit is that record's row of the project state's checkpoint log, since a generated file cannot hold its own commit. Its banner states how each link of owner decisions 14's §31 chain is reached, from its columns or the registry's, without a second registry (the stage record's "Carried to checkpoint D").
- The matrix's second table lists the other requirements a marker names, each with the disposition the plan's section 3 gives it; its third lists every test module with its number of test functions and how many name a requirement, so a test without a requirement is visible, as U7's purpose asks, by module. A test that names none still runs at every checkpoint and on every push.

**What the checker now refuses** (each with its self-test case, and each check with its mutation): a marker that names no requirement; a marker that names an unknown requirement, or one that is not approved (PROPOSED, FUTURE, PREVIOUSLY DISCUSSED / REQUIRES CONFIRMATION, or DEPRECATED / REPLACED: ARCH-029, GOV-017); a `req` marker that takes anything other than requirement IDs written as strings, does not decorate a test function, or is not written on one line as a decorator; a requirement of the plan's section 3.1 without an implementation marker, or without a test or check marker; a unit of section 3.1 in no checkpoint of the stage record; and a matrix out of date, edited by hand or left behind by a change.
