# DEC-045 — Apply the Foundation convergence audit: how the remaining gates are briefed, classified, and re-run

- **Status:** ACCEPTED
- **Date:** 2026-10-13
- **Decided by:** project owner (the rules of [owner decisions 13](../handoffs/owner-decisions-13-foundation-verification-convergence-audit.md), the Foundation verification convergence audit directive); the builder's: how they apply to the existing three-gate procedure, from the audit's findings
- **Applies to:** the rest of Stage 1 (checkpoints C and D, and the stage's own gates), and to later work until a later decision changes it

## Context

The [Foundation convergence audit](../traceability/foundation-convergence-audit-2026-10-13.md) found Stage 1 converging, with no open blocking finding, but checkpoint B passed its third gate only on the eleventh independent run. Of its 26 blocking findings, most were genuine defects against the approved plan; the slow tail had process causes: the records claimed more than the code enforced and the baseline required; the reviewer briefs made "a rule not enforced as claimed" blocking, so every rule the builder added became new blocking surface, and the briefs were not kept in the repository; optional findings were fixed by adding rules that later produced blocking findings; some fixes caused new blocking findings; and some re-runs were broader than the change required. Owner decisions 13 asks that these be corrected without lowering the standard (its §16, §32, §38), and without a new gate, review lifecycle, or governance system (its §1).

## Decision

1. **Each Gate 3 brief gives the approved baseline** (owner decisions 13, §31): the units in scope with their acceptance criteria, the Gate 3 definition of the [Stage 1 plan](../roadmap/stage-01-foundation-plan.md) (§8), the completion criteria (§9), the non-scope (§5), the canonical rules that apply, and the current state. It never states a desired conclusion. The verification record keeps each brief's baseline and its severity definition, so the target each run checked is in the repository ([traceability README](../traceability/README.md)).
2. **A finding is blocking only with its provenance** (§6, §7, §11): it names the approved requirement, decision, plan acceptance criterion, constitution rule, or owner instruction it shows violated, or it shows a statement in the records that is false or overstated. The builder's own conventions are not provenance by themselves; a false statement in them is. A finding with neither is recorded as non-blocking, a proposal, or later work, in its canonical place. Severity is not raised because an improvement is desirable, nor lowered because a fix is inconvenient.
3. **Findings keep one identity** (§5): they are numbered once per checkpoint, across its runs (for checkpoint C: C-01, C-02, and so on), and each new finding says whether it is new, a duplicate, a reopened finding, a regression caused by a fix, or related to an earlier one.
4. **The records claim only what is enforced, and fixes stay within the baseline** (§3, §17, §18; constitution Rules 128, 129): a record states what the code enforces and lists its limits ("What the rules do not catch"). A false claim is fixed by stating the truth. A fix adds enforcement beyond the baseline only where a canonical source requires it. A non-blocking or optional finding whose fix would add a new rule is recorded for later, not fixed in the same round; a fix of wording is applied.
5. **Revalidation follows the impact of a change** (§9, §10, §14, §28): a fix covers the finding's class, not only the reported path. After a fix, the checks the change can affect run again, each as its own command. A Gate 3 run after a failed one reviews the fixes, what they touch, and the tree's difference from the previous run's copy, unless the change is broad. A fix of wording that the review itself specified, that changes no requirement, decision, owner answer, or verbatim text, needs no further independent run (as at the [final decision checkpoint](../traceability/final-decision-checkpoint-2026-10-05.md) and the [quality audit](../traceability/quality-audit-2026-10-06.md)); the record then states the failed run and that its wording was applied without a further run. Evidence that a change invalidates is named, with the reason, in "Failures and fixes".
6. **Check 7 keeps its per-rule standard** (§12): every rule the code enforces has a test that fails when the rule is removed (master execution constitution §148, "What enforcement has no test?", and §76 for approved machine-enforceable rules; DEC-032, Verification 3). No score is set. A surviving mutation is analysed: a missing test is added; a mutation without effect is recorded. During a checkpoint's rounds, the mutations of changed code and of rules whose tests changed are run; the full list runs once on the checkpoint's final tree. The list of mutations and the script that applies them are kept in the repository from checkpoint C, committed with its work, so another session can repeat check 7 (master execution constitution §22).
7. **Convergence is tracked** (§15, §16, §34): each verification record counts, per Gate 3 run, the blocking findings and how many were reopened or caused by fixes. If a run does not lower the blocking count, or a fix causes a blocking regression, the builder makes a root-cause review before the next run. The cycle ends when no blocking finding remains; later improvements go to their canonical place, and the checkpoint is not reopened for them.
8. **The exit checklist** is kept in the [stage record](../traceability/stage-01-foundation.md), "Transition checklist and completion certificate": plan §9's eight criteria, with the §152 items under the sixth, each with its evidence and status. It restates the approved criteria and adds none (§19, §20).
9. **Whether owner decisions 13 joins the builder texts** that `CLAUDE.md` loads is decided with owner decisions 9's adoption ([DEC-044](DEC-044-preserve-archive-tag-answers-and-convergence-audit.md), decision 4); until then it applies through this record.

## Alternatives considered

- **Keep the briefs and the handling of findings as they were.** Rejected: the audit shows the verified surface grew with the records' claims, and checkpoint B's tail came from that.
- **Make findings non-blocking unless they concern security.** Rejected: it would hide real defects; most of checkpoint B's blocking findings were genuine (owner decisions 13, §18, §32).
- **Drop check 7, or set a mutation score.** Rejected: §148 asks of every enforcement whether it has a test (§76 requires one for every approved machine-enforceable rule), and check 7 is the evidence for it; no canonical source sets a score, and none is invented (§12).
- **A separate findings tracker or exit-criteria document.** Rejected: the verification records and the stage record already hold them (§1).

## Consequences

- The [traceability README](../traceability/README.md)'s verification record keeps each Gate 3 brief's baseline and severity, and numbers findings per checkpoint.
- The stage record's "Transition checklist and completion certificate" is kept from now on, not only at checkpoint D.
- No requirement, plan criterion, or earlier decision changes; nothing here authorizes work beyond DEC-038's Stage 1.
