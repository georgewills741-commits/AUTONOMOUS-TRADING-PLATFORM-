# DEC-054 — The owner's instruction of 2026-10-27 to fix the limits on record: a limit on a configuration file's size (V-41); the temporary backup branches retired (owner decisions 22)

- **Status:** ACCEPTED
- **Date:** 2026-10-27
- **Decided by:** project owner ([owner decisions 22](../handoffs/owner-decisions-22-configuration-limit-and-branch-retirement.md): the instruction to fix the limits on record, given in answer to the builder's offer to add a limit on a configuration file's size, and the two rule sets); the builder's, under that instruction and those rule sets: the limit's value and how it is enforced (decision 3), and where the branches' retirement is recorded (decision 4)

## Context

Stage 1's checkpoint C was committed on 2026-10-27 (`b11abe7`), and the builder's report listed, as item 8, its "Limits on record":

- a configuration file larger than available memory stops the load with a Python error, not a clean refusal (finding C-18 of the [checkpoint C verification](../traceability/stage-01-checkpoint-c-verification.md), stated in the [developer guide](../development.md)'s "What the rules do not catch");
- this environment refused (HTTP 403) to delete the temporary backup branches of checkpoints B and C and of item 3, whose content their archive branches keep ([DEC-052](DEC-052-apply-owner-answers-on-order-of-work-and-backups.md), decisions 3 and 4).

At 07:29 UTC the owner asked what the first limit means. The builder answered that the command reads each file whole before checking it, that only a file too large for memory escapes the clean refusal, that the load still fails closed, and that reaching the case takes a multi-gigabyte file. It offered to add a limit on a file's size, such as 1 MB, as a value recorded in the [values register](../requirements/values-register.md), since ARCH-018 requires that of any such value. At 07:59 UTC the owner answered: fix all these problems if possible, safely, and treat that as a rule. The same message sets two rule sets: one for temporary branches whose deletion is refused, one for the configuration's resource safety. Measured for this change ([verification record](../traceability/owner-decisions-22-verification.md)), the builder's answer understated the first limit:

- Python's TOML reader takes memory and time that grow with the square of a dotted key's parts. A document of 32 KiB holding one such key took the process about 1 GiB, and one of 64 KiB about 4 GiB; with its memory capped at 1 GiB, the command failed with `MemoryError` on such a file of 64 KiB. A file of tens of kilobytes is enough, not one of gigabytes, and a limit of 1 MB would not have bounded the memory.
- Under an address-space limit, the allocation fails with `MemoryError` (C-18's reproduction). Without one, Linux can let the allocations succeed until its out-of-memory killer stops the process, or another one, with no Python error at all. This is inferred from Linux's documented behaviour and not reproduced here, since it could stop other processes.

The load stayed closed: `load_configuration` returns a whole configuration or raises, keeps no state, and nothing reloads a configuration at run time, so no partial or corrupted configuration could result; and neither the traceback nor a refusal printed a secret or the file's content.

## Decision

1. **Owner decisions 22 is preserved word for word**: the two messages, as a HISTORICAL source listed in the preserved-text manifest. Each was taken by script from its own user turn in the session record and kept byte for byte, including the spaces that end three of its lines. The client's "Continue from where you left off." prompts and the owner's "Continue" messages sent while this change was made, the first at 10:37 UTC, are procedural ([DEC-047](DEC-047-preserve-stage-transition-persistence-rules.md), decision 7; [owner decisions 16](../handoffs/owner-decisions-16-short-instructions-approvals-and-questions.md)); the [verification record](../traceability/owner-decisions-22-verification.md) names each. The owner's question of 17:07 UTC on the stage the work is at, sent between this change's Gate 3 runs, is preserved word for word too, as [owner decisions 23](../handoffs/owner-decisions-23-question-on-the-stage.md), HISTORICAL and listed in the manifest. It changes nothing: the builder answered it in its report at the end of that turn, at 17:24 UTC, and its instruction to continue while answering is how the work went on.
2. **The instruction to fix the limits on record is applied, not stated again.** Fixing a known problem, safely, whenever the correct solution is established is already a rule: the [quality directive](../builder/quality-consistency-and-correction-directive.md) (§6, §16), the [builder constitution](../builder/claude-code-builder-constitution.md) (Rule 125), and owner decisions 9 (Rule 28). So no rule is added ([owner decisions 17](../handoffs/owner-decisions-17-reuse-reinforce-and-enhance-existing-controls.md), Rule 0; [DEC-048](DEC-048-preserve-and-apply-rule-0.md)). This change comes before checkpoint D, at the owner's instruction; the order [DEC-052](DEC-052-apply-owner-answers-on-order-of-work-and-backups.md) set is otherwise unchanged. Of the limits on record:
   - the first is fixed (decision 3);
   - the branches cannot be deleted from this environment: this session's access to GitHub refuses it (HTTP 403), though the branches are not protected on GitHub. They are retired as the owner's first rule set provides (decision 4);
   - the note that the owner can delete them on GitHub's Branches page stays an option for the owner.
3. **A configuration document has a size limit: V-41, an IMPLEMENTATION CHOICE in the values register**, whose row holds the value and its reason.
   - **No control existed.** The requirements, the system rules, the values register, the code, and the tests had no limit on a configuration's size, an input's size, or a resource. The rules that cover it are constitution Rules 108 (configuration validated before use) and 150 (no uncontrolled memory growth), the master execution constitution's §115, and the Stage 1 plan's U4 ("Fail closed"). The limit reinforces them with one value, one constant, and one register entry.
   - **What `atp.config` does.** It reads at most one byte more than the limit from a file, so a larger file is refused without being read in full. `read_toml` refuses a longer text before parsing it. Each refusal is a `ConfigurationError` that names the file and the limit and holds nothing from the file.
   - **Who decided what.** The owner decided that the limit be added: the instruction of 07:59 answers the builder's offer. The value is the builder's, an IMPLEMENTATION CHOICE ([DEC-020](DEC-020-value-classification.md): a mechanism choice), resting on the engineering reasons the owner's rule asks for: the size of the configuration in use, and the reader's measured worst case. No requirement, policy, or authority changes, and no valid configuration's behaviour changes, since every file in use is under a ninth of the limit. Another value is a change to V-41, the constant `atp.config.MAXIMUM_DOCUMENT_SIZE`, and the test that pins it.
   - **`MemoryError` is not caught.** Within the limit, the reading's memory is bounded, so a `MemoryError` would be a failure of the host, which the configuration does not cause. Reporting it as a refused configuration would name the wrong cause (the owner's rule, §6: catch only what is justified).
   - **No last-known-good behaviour is built.** The owner's rule asks for it where configurations are reloaded at run time (§7, §8). Nothing reloads one: a process loads its configuration once, at start, and a refused load leaves nothing behind. That behaviour belongs to the stage that first reloads a configuration.
4. **The three temporary backup branches are RETIRED — DELETION BLOCKED — SAFE TO DELETE WHEN PERMITTED**: `claude/unverified-backup-checkpoint-b`, `claude/unverified-backup-item-3`, and `claude/unverified-backup-checkpoint-c`.
   - **No authority.** None of them is used, merged, or developed from, or read as the project's state. Each archive branch stays the reference for its backup's commits (DEC-052, decision 3).
   - **Where it is recorded.** Each branch's fields, as the owner's rule lists them, are in the [project state](../project-state.md)'s record of branches, the existing mechanism. No register, branch, or rename is added to retire them; this change's own temporary backup is DEC-052's (decision 3), and the project state records it as active.
   - **Checks.** The ten checks the owner's rule requires before "safe to delete" passed for each branch on 2026-10-27 ([verification record](../traceability/owner-decisions-22-verification.md)).
   - **When deletion is tried again.** Not while the 403 holds. Only on evidence that this environment's access has changed, or at the owner's request, and only after re-checking that each branch is still retired and at its archived commit. After a deletion succeeds, the record says RETIRED — PHYSICALLY DELETED. If the owner deletes them on GitHub, the next session records that.
   - **Later backups.** A later temporary backup (DEC-052, decision 3) is retired the same way if its deletion is refused.
5. **The two rule sets stay in force through this decision record**, as the rule sets of owner decisions 13 to 15 and 17 stay in force through theirs ([DEC-051](DEC-051-adopt-requirement-drafting-and-anti-drift-rules.md), decision 3). `CLAUDE.md` names them, and the [owner rule sets reconciliation](../traceability/owner-rule-sets-reconciliation.md) maps each of their rules to the text that already states it or the mechanism that applies it. No builder text is added to or changed.
6. **Nothing else changes.** No requirement is added, removed, or changed: V-41 is a value, recorded as ARCH-018 requires. No gate or system rule changes. Nothing here authorizes work beyond [DEC-038](DEC-038-stage-1-plan-approved.md)'s Stage 1; checkpoint D follows.

## Alternatives considered

- **Keep the limit stated in the developer guide** (the state after checkpoint C). Not chosen: the owner asked for it to be fixed, and a file of tens of kilobytes reaches it.
- **A limit of 1 MB, the builder's example of 07:29, or any limit much larger than V-41.** Not chosen: the reader's worst case grows with the square of the size, so such a limit would leave the memory unbounded in practice.
- **A smaller limit, such as 4 KiB.** Not chosen: under five times the largest configuration file in use.
- **Counting a key's dotted parts before parsing, so that larger files are allowed.** Not chosen: that needs a second TOML tokenizer, complexity the configuration does not need now (the owner's rule, §5).
- **Catching `MemoryError` at the reading's boundary.** Not chosen: decision 3.
- **Limiting the process's memory** (for example with `resource.setrlimit`). Not chosen: it applies to everything the process does, not only to the configuration, and is not available alike on every system.
- **A new register of branches, new branches marking retirement, renamed branches, or repeated deletion attempts.** Not chosen: the owner's rule rules out the register, the new branches, and the attempts (§3, §4, §6); and a rename needs a new branch and the old one's deletion, which this environment refuses, so it would leave a duplicate (§7).
- **Loading the two rule sets as builder texts.** Not chosen: most of their rules are already stated, and a second statement would compete with the first (DEC-051, decision 3; owner decisions 9, Rules 3 and 16).

The owner rule sets reconciliation and `CLAUDE.md` name the two rule sets, and this change's verification record holds the reconciliation of checkpoint C's temporary backup with `b11abe7`.
