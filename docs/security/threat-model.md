# Threat Model

> **Status:** ACTIVE — the platform's design-level threat model, written at Stage 1's checkpoint C (U5 of the [Stage 1 plan](../roadmap/stage-01-foundation-plan.md); location set by its decision D2) · **System:** SYS-31 Security Architecture · **Requirements:** SEC-001 (the assets), with the security requirements of the [security architecture](security-architecture.md) and the others named below, each in its owning specification
>
> For each asset of SEC-001 and each trust boundary, what could go wrong, the controls the requirements already require, what Stage 1 builds, and the gap: each requirement it names that Stage 1 does not deliver (the Stage 1 plan's section 3.1), with its stage, which is the [registry](../requirements/registry.md)'s default stage unless the [roadmap](../roadmap/roadmap.md) or the Stage 1 plan's section 3.2 or 3.4 places it later. It is design-level only and adds no requirement: a new requirement it suggests goes through the [findings register](../conflicts/register.md) first, and it suggests none now.

## Security traceability of Stage 1's controls

Each control U4 and U5 build in Stage 1, traced from its requirement (owner decisions 14, §21: requirement → control → implementation → test → verification → monitoring). The checkpoint A controls named in the trust boundaries above (the machine checks' read-only permissions, no repository secret, and actions pinned by commit, U6 and D4; the dependency review, U1) have no test of their own; their evidence is in the [stage record](../traceability/stage-01-foundation.md)'s "Machine checks on GitHub (U6 acceptance)" and "Checkpoint A: versions, dependency review, and licenses".

| Requirement | Control | Implementation | Tests | Verification | Monitoring |
|---|---|---|---|---|---|
| SEC-005 | No secret-like file or value is committed; a secret declaration in a TOML file holds only a valid name and kind, as the configuration's own contract reads them | `tests/repository/test_no_secrets.py` | The same module's planted samples, including planted secrets in copies of the example configuration | The gates of checkpoints A and C | The machine checks run it on every push (GOV-023) |
| SEC-005 | Secret values come only from the process environment, through `atp.config.SecretSource`; a `Secret` is never shown, pickled, or copied, and gives out no state; a configuration whose file, or a setting's value as read, holds a declared secret's value is refused | `src/atp/config/` | `tests/config/test_secrets.py`, `tests/config/test_load.py`, `tests/cli/test_cli.py` | Checkpoint C's gates | None: Stage 1 runs no service |

No security exception is in force. Ruff's security rules (`S`) are suppressed nowhere in `src/`. In `tests/`, `assert` (`S101`) is allowed in every test file by `pyproject.toml`, which gives the reason, and each other suppression gives its reason on its line: unpickling bytes the test itself made, running fixed test strings, running git with fixed arguments, and running the test's own interpreter with fixed arguments. In `tools/mutation/run.py`, the one suppression gives its reason on its line: running uv with fixed arguments, without a shell.
