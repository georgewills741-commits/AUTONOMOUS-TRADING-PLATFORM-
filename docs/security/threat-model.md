# Threat Model

> **Status:** ACTIVE — the platform's design-level threat model, written at Stage 1's checkpoint C (U5 of the [Stage 1 plan](../roadmap/stage-01-foundation-plan.md); location set by its decision D2) · **System:** SYS-31 Security Architecture · **Requirements:** SEC-001 (the assets), with the security requirements of the [security architecture](security-architecture.md) and the others named below, each in its owning specification
>
> For each asset of SEC-001 and each trust boundary, what could go wrong, the controls the requirements already require, what Stage 1 builds, and the gap the stage that owns each control must close (its stage is the [roadmap](../roadmap/roadmap.md)'s, or the Stage 1 plan's section 3.4 where it places a requirement later). It is design-level only and adds no requirement: a new requirement it suggests goes through the [findings register](../conflicts/register.md) first, and it suggests none now.

## Assets (SEC-001)

With a single operator ([DEC-006](../decisions/DEC-006-single-operator-and-trading-ledger.md)), "user accounts" means the operator's own access to the platform.

| Asset | What could go wrong | Controls already required | Built in Stage 1 | Gap, and the stage that closes it |
|---|---|---|---|---|
| Exchange credentials and API keys | Committed, logged, shown in an error, or put in an AI prompt; present outside production; carrying withdrawal permission; used from another address; changed by research | SEC-005; SEC-004 and MODE-006 (trading-enabled credentials only in production); OPS-004; PAP-011; SEC-006 (no withdrawal permission; known IP addresses where the venue supports it); SEC-007; STR-008; SEC-002 and SEC-008; MIG-009 | The repository's secret test (U1, U5); a configuration declares each secret by name and kind, never by value, its value comes only from the process environment and is never shown, and a trading-enabled credential is refused outside production (U4) | No credential exists in Stage 1. Their venue-side permissions (SEC-006): the stage that first holds credentials (SEC-004; the Stage 1 plan, section 3.2); transfer credentials (SEC-006, SEC-007): ARBITRAGE; a secret manager behind the same interface (SEC-005) and key management (SEC-009): OPERATIONALIZATION |
| Other secrets: server and AI credentials | As above; an AI credential held outside the AI gateway | SEC-005; SEC-004 and AIL-006 (AI credentials only at the AI gateway); MIG-009 | As above: the configuration's secret kinds `server` and `ai` | The database: DATA FOUNDATION; the AI gateway: AI INTELLIGENCE |
| Wallet keys, where applicable | A key that could move funds outside the operator's accounts | SEC-006: the platform holds no withdrawal or custody authority (custody is FUTURE, CUS-002) | The configuration's closed set of secret kinds has no withdrawal or custody kind, so none can be declared | None while custody stays FUTURE |
| User accounts (the operator's access) | Someone other than the operator acts as the operator | SEC-009 (authentication, authorization); POL-010 (a validated operator interface for policy edits); POL-005 (important changes need confirmation) | Nothing: Stage 1 has no operator interface | Authentication for the operator interface is not yet specified (the [security architecture](security-architecture.md), "Not yet specified"). The interface comes with POL-010 in CORE TRADING FOUNDATION, while SEC-009 puts authentication in production hardening (OPERATIONALIZATION), so it is specified when CORE TRADING FOUNDATION is planned |
| Trading permissions | An order from an environment other than production; two instances trading one account; authority raised by AI or research | MODE-006; OPS-004; PAP-011; EXE-010 and REC-013 (the execution lease); RSK-010 (no order without the Risk Engine's authorization and a capital reservation); AIL-003; SEC-008; STR-008 | Defence in depth only: a trading-enabled credential is refused outside production (U4). The real barrier, that no trading credential exists outside production, is not something code can provide | CORE TRADING FOUNDATION (the execution lease, the Risk Engine); AI INTELLIGENCE (the AI's limits) |
| Financial records | An amount rounded silently or held as a float; a second copy of the ledger; a record changed or lost | ARCH-010 and TEC-003 (exact amounts); LED-003, LED-004, LED-006; TEC-012 (append-only, kept permanently) | Exact amounts and contracts that refuse floats and JSON numbers for amounts (U2, U3) | The ledger: CORE TRADING FOUNDATION |
| Audit records | Deleted, altered, mixed with operational logs, or missing | AUD-001, AUD-002, AUD-004, AUD-006; TEC-012 | Nothing: Stage 1 has no audit trail | CORE TRADING FOUNDATION |
| AI access | AI given unrestricted credentials, a secret in a prompt, a tool used beyond its role | SEC-002; SEC-005 (never in AI prompts); SEC-008; AIL-003; AIL-006; AIL-013; AGT-022; AIV-004 | Nothing: Stage 1 has no AI (plan section 5) | AI INTELLIGENCE |
| Administrative operations | An unauthorized deployment, configuration change, or kill-switch reset | SEC-009; SEC-008 (no research agent receives production deployment permission automatically); OPS-010 (one deployment definition); RSK-025 (AI cannot activate or reset a kill switch) | A configuration is validated before use and refused in full on any error (U4; constitution Rule 108); the machine checks hold no secret and deploy nothing (U6) | OPERATIONALIZATION |

## Trust boundaries

| Boundary | What crosses it | Controls already required | Built in Stage 1, and its limits | Gap |
|---|---|---|---|---|
| The six environments (OPS-004) | Configuration and credentials | Each environment has its own configuration, database, and credentials (OPS-004); only production holds trading-enabled credentials (MODE-006, SEC-004); paper never touches live accounts (PAP-011) | An environment's identity comes from its own file, and the `--env` a process is run with must be the one the file declares; a trading-enabled credential is refused outside production (U4). These read what a configuration declares: they cannot see a credential's real permissions at the venue | Separate databases and credentials per environment: OPERATIONALIZATION (OPS-004) |
| The AI gateway | AI credentials, prompts, tool calls | SEC-004, AIL-006, AIL-013, SEC-008, AGT-022, AIV-004 | Nothing: no AI | AI INTELLIGENCE |
| Exchange credentials (the platform and each venue) | Orders, balances, transfers | SEC-005; SEC-006; SEC-007 | Secrets come only from the process environment, through one interface a secret manager can implement later (U4) | CORE TRADING FOUNDATION, ARBITRAGE, OPERATIONALIZATION, as above |
| The three credential authorities of SEC-006 | Trading, rebalancing transfers, withdrawal and custody | SEC-006: separate credentials; the platform holds no withdrawal or custody authority | The configuration can declare only the kinds `trading`, `ai`, and `server` (U4): no transfer or withdrawal kind exists yet | A transfer kind is added, with its rule, when ARBITRAGE needs one |
| The operator interface | The operator's commands and policy edits | SEC-009; POL-005; POL-010 | Nothing: no operator interface | Authentication, specified when CORE TRADING FOUNDATION, which builds the interface (POL-010), is planned (the user accounts row above) |
| The repository and its machine checks | Code, configuration examples, workflow runs | SEC-005; constitution Rules 110 and 153; GOV-023 | The secret test scans every file git tracks or would add, including the example configuration, whose secret declarations may hold only a name and a kind (U1, U5); the machine checks have read-only permissions, reference no secret, and pin their actions by commit (U6, D4); the locked dependencies were checked against published advisories ([stage record](../traceability/stage-01-foundation.md), checkpoint A) | Vulnerability monitoring: OPERATIONALIZATION (SEC-009) |

## Security traceability of Stage 1's controls

Each control built in Stage 1, traced from its requirement (owner decisions 14, §21: requirement → control → implementation → test → verification → monitoring).

| Requirement | Control | Implementation | Tests | Verification | Monitoring |
|---|---|---|---|---|---|
| SEC-005 | No secret-like file or value is committed; a secret declaration in a TOML file holds only a name and a kind | `tests/repository/test_no_secrets.py` | The same module's planted samples, including planted secrets in copies of the example configuration | The gates of checkpoints A and C | The machine checks run it on every push (GOV-023) |
| SEC-005 | Secret values come only from the process environment, through `atp.config.SecretSource`; a `Secret` is never shown, pickled, or copied; a configuration whose file holds a declared secret's value is refused | `src/atp/config/` | `tests/config/test_secrets.py`, `tests/config/test_load.py`, `tests/cli/test_cli.py` | Checkpoint C's gates | None: Stage 1 runs no service |
| SEC-005 | A refusal never carries the input | `atp.contracts.validation_error_details`; `atp.config.ConfigurationError` | `tests/contracts/test_model.py`; `tests/config/` | Checkpoint B's and C's gates | None |
| MODE-006, SEC-004 (defence in depth) | A trading-enabled credential is refused outside production | `atp.config.EnvironmentConfiguration` | `tests/config/test_settings.py`, `tests/config/test_load.py` | Checkpoint C's gates | None |
| OPS-004 | The six environments; each file declares its own; `--env` must match | `atp.config` | `tests/config/` | Checkpoint C's gates | None |

No security exception is in force. Ruff's security rules (`S`) are suppressed nowhere in `src/`; in `tests/`, each suppression gives its reason on its line: unpickling bytes the test itself made, running fixed test strings, and running git with fixed arguments.
